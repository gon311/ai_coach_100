# AI 체력 코치 작업 기록

이 문서는 결과 화면만으로는 잘 보이지 않는 팀의 판단과 시행착오를 남기기 위해 작성했습니다. 프로젝트는 2026년 8월 말 아이디어 정리와 데이터 확인으로 시작해, 9월 말 실행 패키지와 평가 자료를 정리하는 단계까지 진행했습니다.

## 1. 출발점

처음 잡은 문제는 단순했습니다. 국민체력100 측정 결과에는 여러 수치와 등급이 있지만, 사용자가 집에 돌아온 뒤 어떤 운동을 해야 하는지까지 자연스럽게 이어지지 않습니다. 이미 공단이 공개한 측정 데이터와 운동 영상은 충분히 많았으므로, 새 콘텐츠를 만드는 대신 흩어진 자료 사이의 연결을 만드는 쪽에 집중했습니다.

초기 MVP는 다음 다섯 가지로 정했습니다.

1. 센터 측정값 또는 홈 측정값 입력
2. 성별·연령대별 또래 비교
3. 부족한 체력요인에 맞는 운동 추천
4. 추천 근거와 공식 영상 연결
5. 공단 자료를 벗어나지 않는 코칭 대화

주간 루틴과 가까운 센터 안내도 검토했지만, 핵심 흐름의 정확도를 먼저 확보하기 위해 우선순위를 뒤로 미뤘습니다.

## 2. 데이터부터 다시 확인한 이유

기획 단계에서는 측정결과 API 한 종류만으로도 또래 비교와 추천이 가능할 것으로 봤습니다. 실제 파일을 열어보니 측정값, 처방 결과, 추천 규칙, 영상 정보가 서로 다른 구조와 용어를 사용했습니다. 그래서 한 데이터가 모든 판단을 맡지 않도록 역할을 나눴습니다.

- 측정 원시 기록은 백분위 계산에만 사용했습니다.
- 연령별 추천운동은 기본 추천 규칙으로 사용했습니다.
- 실제 처방 사례는 비슷한 조건의 조합을 확인하는 보조 근거로 사용했습니다.
- 영상 데이터는 운동명과 설명, 장소, 장비, 재생 주소를 붙이는 데 사용했습니다.
- 인증기준은 참고값으로만 두고 서비스가 공식 등급을 발급하는 것처럼 표현하지 않았습니다.

이 과정에서 2025년 이후의 6등급 체계와 이전 데이터가 함께 존재한다는 점, 같은 운동도 데이터마다 표기가 조금씩 다르다는 점, 한 편의 전체 프로그램 영상이 준비·본·마무리 행에 반복되는 경우가 있다는 점을 확인했습니다. 화면에서는 26분짜리 전체 프로그램과 1~7분 길이의 개별 운동 가이드를 같은 용도로 보여주지 않도록 분리했습니다.

## 3. 추천을 만드는 방식

추천은 생성 모델이 운동명을 새로 만드는 구조가 아닙니다. 먼저 구조화된 조건으로 후보를 좁히고, 모델은 후보를 설명하는 역할만 맡습니다.

```text
연령·성별·BMI 규칙
        +
운동 목적·부위·장소·장비 조건
        +
현재 프로필의 측정 결과
        ↓
SQLite/Chroma에서 실제 문서 검색
        ↓
운동명·방법·효과·영상 주소를 원문과 대조
        ↓
검증을 통과한 항목만 화면과 답변에 사용
```

질문에 특정 운동명이 들어오면 정확히 일치하는 문서를 먼저 찾고, 운동 방법이나 효과를 설명하는 답변에는 실제 RAG 문서를 최소 한 건 연결했습니다. 질문과 측정값, 인용 문서에 없는 숫자는 답변에서 제거했습니다. 측정 기록이 일부뿐이면 나머지 체력요인을 추정하지 않고 데이터가 부족하다고 말하도록 했습니다.

## 4. 프론트와 백엔드를 맞추는 작업

통합 과정에서 가장 많은 시간이 든 부분은 기능 추가보다 양쪽의 기준을 맞추는 일이었습니다.

- 프론트에서 쓰는 측정 항목 이름과 백엔드 코드값을 하나씩 대조했습니다.
- HOME 결과는 측정 오차를 고려한 상위 비율 구간, CENTER 결과는 점 백분위로 표시했습니다.
- 생애주기 코드를 나이와 함께 모든 추천 요청에 전달했습니다.
- 로그인, 회원가입, 프로필, 기록, 로그아웃 요청에 30초 제한과 실제 요청 취소를 적용했습니다.
- 인증 세션은 기본 24시간 뒤 만료되고, 만료 토큰에 연결된 대화 세션도 함께 지우도록 했습니다.
- 새 게스트나 다른 프로필로 전환할 때 성별·나이·신체정보·측정값·대화 맥락이 초기화되는지 브라우저에서 확인했습니다.

특히 어르신 계정에 성인용 준비운동이 섞였던 문제는 데이터 부족이 아니라 점수 기반 후보 선택 때문이었습니다. 생애주기 일치를 가산점으로만 두지 않고 현재 단계, 공통, 미표기 자료만 후보에 남기는 필터로 바꿨습니다.

## 5. 평가 방법

평가 세트는 정답 문구와의 단순 일치보다 지켜야 할 계약을 기준으로 만들었습니다.

- **R5**: 운동 설명과 수치가 실제 근거 안에 있는가
- **R8**: 질문에 검색이 필요한 경우와 그렇지 않은 경우를 구분하는가
- **R11**: 사용자와 프로필 사이에 기록이 섞이지 않는가

공식 145개 케이스에서 HTTP 응답과 실행 경로를 모두 기록했습니다. 검색 대상 80건은 전부 Chroma 경로를 사용했고 SQLite 키워드 fallback은 없었습니다. 검색 비대상 65건에서는 불필요한 검색이 발생하지 않았습니다.

자동 평가만으로 놓칠 수 있는 부분은 3명이 12개 케이스를 블라인드로 읽고 별도 판정했습니다. 10개는 만장일치, 2개는 의견이 갈렸지만 모두 다수결 PASS였습니다. 의견이 갈린 두 건은 이전 프로필 정보가 섞인 문제는 아니었고, 현재 측정값을 답변에 얼마나 직접 언급해야 하는지에 대한 기준 차이였습니다. 따라서 “12개 모두 통과”만 적지 않고 이 차이도 함께 남겼습니다.

## 6. 확인된 결과

| 구분 | 결과 |
|---|---:|
| 관련 단위·계약 테스트 | 54/54 |
| 공식 평가 세트 HTTP·경로 | 145/145 |
| RAG 검색 대상의 Chroma 사용 | 80/80 |
| R5 근거 제한 | 80/80 |
| R8 검색 경로 | 65/65 |
| R11 프로필 분리 | 6/6 |

실제 화면에서도 HOME 왕복달리기와 상대악력의 구간 표기, CENTER 점 백분위, PAR-Q 차단 뒤 측정 화면 진입, 인증 만료 뒤 401 응답과 세션 정리를 확인했습니다.

## 7. 아쉬운 점과 다음 작업

- 공개 저장소에는 모델과 887MB Chroma 인덱스, 223MB RAG DB를 포함하지 않아 처음 보는 사람이 바로 실행하기는 어렵습니다.
- 3인 블라인드 평가는 12개 케이스로 범위가 작습니다. 실제 사용자 대상의 장기 사용성 평가는 별도로 필요합니다.
- 현재 화면은 일반인 추천을 중심으로 합니다. 장애인 처방 데이터는 분리 보존했지만, 일반 운동 영상을 장애인 맞춤 영상처럼 연결하지 않았습니다.
- 통증과 질환 질문은 운동 참고 정보의 범위를 넘지 않도록 보수적으로 처리했습니다. 의료 판단이 필요한 경우 전문가 상담 안내로 끝냅니다.
- 공공데이터 갱신 시 규준과 추천 규칙을 다시 만드는 절차를 자동화하는 작업이 남아 있습니다.

이번 프로젝트에서 가장 크게 배운 점은 모델 성능만으로 서비스의 신뢰가 생기지 않는다는 것이었습니다. 어떤 데이터가 어느 판단에 쓰였는지, 사용자 정보가 섞이지 않는지, 화면의 한 문장이 실제 API 값과 일치하는지를 끝까지 확인하는 일이 더 오래 걸렸고 결과에도 더 큰 영향을 줬습니다.
