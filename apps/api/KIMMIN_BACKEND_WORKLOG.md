# 백엔드 작업 기록 — 김민

프로젝트가 끝난 뒤 내가 맡았던 일을 다시 정리했다. 당시 Codex에서 주고받았던 대화와 실행 기록을 날짜순으로 확인했고, 기억이 애매한 부분은 팀 문서와 실제 코드도 같이 봤다.

내가 주로 맡은 쪽은 백엔드와 사용자 DB, 로컬 Qwen3 및 RAG 연결, Windows 실행 패키지였다. 프로젝트 후반에는 화면에서 발견한 문제를 백엔드까지 따라가며 고친 일이 많아서 프론트 작업도 일부 포함되어 있다.

작업 기간은 2026년 8월 26일부터 9월 30일까지 약 5주였다.

## 1주차 — 8월 26일~9월 2일

### 데이터를 어떻게 저장하고 사용할지 정리

처음에는 국민체력100 측정결과 데이터만 있으면 또래 비교와 운동 추천을 모두 만들 수 있을 거라고 생각했다. 그런데 파일을 실제로 확인해 보니 측정 데이터, 운동 추천 데이터, 영상 데이터가 따로 있었고 각 파일의 기준도 달랐다.

그래서 먼저 팀에서 정리한 데이터 기준을 받아 백엔드에서 어떻게 저장할지 확인했다.

- 센터 측정과 홈 측정을 테이블 두 개로 나누지 않고 `source` 값으로 구분
- 홈 측정도 센터 규준을 사용하되 결과는 오차를 고려한 구간으로 표시
- 절대악력(kg)과 상대악력(%)은 서로 다른 측정값으로 저장
- 원본 데이터와 사용자 기록 DB는 공개 저장소에서 제외

특히 홈 측정값을 별도의 가상 분포와 비교하지 않고, 실제 센터 측정 분포에 넣은 다음 측정 오차를 결과 구간에 반영하는 방식으로 정리했다. 이후 HOME과 CENTER API를 만들 때 이 기준을 계속 사용했다.

이 시기의 Codex 대화는 남아 있지 않다. 세부적으로 어느 파일을 얼마나 수정했는지까지는 확인할 수 없어서, 팀 문서에 남아 있는 백엔드 전달 내용만 적었다.

관련 문서:

- `docs/planning/status-archive.md`
- `docs/planning/meeting-02/측정데이터_정규화_스펙_v1.md`
- `docs/planning/meeting-02/홈측정_설계기준_v2.md`

## 2주차 — 9월 3일~9월 9일

### 로컬 모델 실행 환경 정리

9월 7일부터는 모델과 서비스 연결 작업을 시작했다. 당시 E 드라이브에 Qwen 모델과 UI가 여러 개 있었고 어떤 포트에서 어떤 모델이 실행되는지부터 다시 확인해야 했다.

27B 모델과 프로젝트에서 사용할 Qwen3-4B가 섞이지 않도록 실행 환경을 따로 만들었다.

- Qwen3.8 27B UI: `8088`
- 프로젝트용 Qwen3-4B UI: `8089`
- Qwen3-4B 설정: context 32,768 / 최대 생성 8,192 토큰
- 모델별 시작·종료 PowerShell 스크립트 작성

스크립트를 만든 뒤에는 실행만 확인한 것이 아니라 종료 후 다시 시작해도 같은 설정으로 올라오는지 확인했다. Qwen3의 경우 짧은 답변이 내부 추론에 모두 사용되어 화면에 답이 나오지 않는 경우가 있어서 `enable_thinking: false` 설정도 함께 적용했다.

### 프론트 화면을 실제 백엔드에 연결

처음 받은 `frontend1`은 화면은 만들어져 있었지만 일부 기능이 MOCK 데이터로 동작하고 있었다. 기존 화면을 새로 만드는 것보다, 현재 화면에서 실제 API를 호출하도록 연결하는 방향으로 진행했다.

통합 주소는 `http://127.0.0.1:8501`로 잡았고 다음 항목을 하나씩 확인했다.

- `/api/health` 응답
- Qwen3-4B 모델 연결
- Chroma 인덱스 로드
- RAG 문서 160,461건 확인
- `/api/coach`, `/api/chat` 실제 응답
- 프론트 페이지 HTTP 200

서버와 모델을 각각 실행하면 팀원이 사용하기 어렵기 때문에 프론트, 백엔드, 모델을 같이 올리고 내릴 수 있는 시작·종료 스크립트도 만들었다.

### 측정값을 또래 백분위로 계산

다음으로 사용자가 입력한 측정값을 같은 성별과 5세 연령대의 기록과 비교하도록 연결했다.

처음에는 화면에 6개 항목의 평균을 모두 표시하려고 했는데, 원본 데이터를 확인해 보니 연령대마다 공식 측정종목이 달랐다. 성인 데이터에는 근지구력과 순발력이 있고, 어르신 데이터에는 심폐지구력과 하지근기능이 있었다. 없는 평균을 다른 연령대에서 가져오면 비교 기준이 달라지기 때문에 그렇게 하지 않았다.

연결한 주요 항목은 다음과 같다.

- 앉아윗몸앞으로굽히기
- 교차윗몸일으키기
- 2분 제자리걷기
- 제자리멀리뛰기
- 의자 앉았다 일어서기
- 악력

악력은 처음에 원본 필드가 확실하지 않아 화면에 임시 안내를 표시했다. 이후 데이터 정의서를 다시 확인해 상대악력과 절대악력 필드를 찾았고, 사용자가 입력한 악력과 체중으로 `악력÷체중×100`을 계산해 상대악력 백분위에 연결했다.

규준을 만들 때는 원본 CSV 55개, 1,433,939행을 집계했다. 같은 성별·연령대의 값이 없는 항목은 억지로 평균을 채우지 않고 화면에 비교 기준이 없다고 표시했다.

### 공식 영상과 챗봇 연결

측정 결과 옆에서 해당 체력요인의 운동 영상을 볼 수 있도록 국민체력100 영상 데이터를 API에 연결했다. 항목별 공식 영상 3개가 반환되는지 확인했고, 결과 화면의 챗봇은 다음 흐름으로 연결했다.

`결과 화면 → /api/chat → qwen3_grounded_harness.py → Qwen3-4B`

사용자가 결과 화면에서 챗봇을 열면 부족한 체력 항목이 먼저 문맥에 들어가도록 했다. 첫 추천과 그다음 질문이 같은 문맥에서 이어지는지도 실제 응답으로 확인했다.

주로 본 파일:

- `apps/api/src/fitness_web_server.py`
- `apps/api/src/fitness_mvp.py`
- `apps/api/src/qwen3_grounded_harness.py`
- `apps/api/src/center_percentile.py`
- `apps/api/scripts/`

## 3주차 — 9월 10일~9월 16일

### 어르신 계정에 성인 영상이 나온 문제

테스트 계정 `test2`는 72세 여성이었는데, 운동 추천을 확인하니 준비운동에는 성인 영상이 나오고 본운동과 마무리운동에는 어르신 영상이 나왔다.

처음에는 어르신 준비운동 데이터가 없어서 그런 줄 알았다. 하지만 원본 JSON을 확인해 보니 어르신 영상은 충분히 있었다. 문제는 영상 선택 방식이었다. 당시 코드는 연령대가 맞으면 점수를 더 주는 방식이었고, 필수 조건은 아니었다. 그래서 제목이나 설명에 검색어가 많이 포함된 성인 영상이 더 높은 점수를 받으면 그대로 선택됐다.

이 문제는 가산점으로 해결하기 어렵다고 판단했다. 프론트에서 `age`와 `life_stage`를 함께 보내고, 백엔드에서 두 값이 맞는지 검사하도록 바꿨다. 그다음 현재 생애주기와 공통 영상만 후보로 남긴 뒤 점수를 계산하도록 순서를 바꿨다.

한 번에 수정되지는 않았다. 첫 작업에서는 Codex 보안 체크포인트 오류로 패치가 적용되지 않았다. 같은 작업에서 계속 시도해도 파일이 바뀌지 않아 새 작업을 만든 뒤 다시 재현하고 수정했다. 이때 실패한 작업을 성공한 것처럼 정리하지 않고 별도 기록으로 남겨 두었다.

### 사용자 기록과 대화가 섞이지 않는지 확인

로그인 기능이 있다고 해서 사용자 분리가 자동으로 되는 것은 아니었다. 사용자 A가 로그아웃하고 사용자 B로 들어갔을 때 이전 측정 기록이나 챗봇 대화가 남을 가능성이 있었다.

그래서 다음 부분을 따로 확인했다.

- 측정 세션을 현재 사용자 ID로 조회하는지
- 기록 소유자와 로그인 사용자가 같은지
- 프로필이 바뀌면 이전 대화가 새 문맥에 들어가지 않는지
- 비회원으로 다시 시작할 때 이전 입력값이 초기화되는지
- 이전 기록 비교에서 현재보다 나중에 생성된 기록이 잘못 선택되지 않는지

HOME과 CENTER 결과도 다시 맞췄다. HOME은 자가측정 오차가 있으므로 백분위 구간을 반환하고, CENTER는 장비 측정값이므로 점 백분위를 유지했다. 상대악력과 절대악력도 연령에 맞게 구분했다.

이 과정에서 백엔드가 상세 오류를 보내도 프론트 서비스 코드가 모두 `api-unavailable` 같은 한 문장으로 바꾸는 문제도 발견했다. 실제 원인을 확인할 수 있도록 오류 전달 방식을 같이 점검했다.

## 4주차 — 9월 17일~9월 23일

### 인증 요청이 끝없이 기다리는 문제

로그인이나 기록 조회에서 서버 응답이 늦어지면 화면이 계속 대기 상태로 남아 있었다. fetch에만 제한 시간을 두는 것으로는 부족했고, 응답을 받은 뒤 JSON을 읽는 과정도 멈출 수 있어야 했다.

로그인, 회원가입, 프로필, 기록, 로그아웃 요청에 기본 30초 timeout을 넣었다. `AbortController`를 사용해 요청과 응답 파싱을 모두 취소할 수 있도록 했다.

### 로그인 토큰 만료 처리

기존 인증 세션은 생성시각을 저장하고 있었지만 실제 만료 검사가 없었다. 기본 만료시간을 24시간으로 두고 `AI_FITNESS_AUTH_TTL_HOURS` 환경변수로 바꿀 수 있게 했다.

만료됐거나 생성시각이 잘못된 토큰은 401을 반환하고, 그 토큰으로 만들어진 서버 대화도 같이 지우도록 했다. 테스트용 만료 토큰을 DB에 직접 넣는 과정에서 실행 중인 DB가 읽기 전용으로 잡혀 한 번 실패했다. 관리자 권한으로 다시 실행한 뒤 API 호출 후 토큰과 대화가 실제로 삭제되는 것을 확인했다.

### 프론트와 백엔드의 백분위 구간 맞추기

HOME 결과의 구간 폭도 다시 대조했다. 프론트 레이더 설정과 백엔드 계산값이 다른 항목이 있었고, 특히 10m 왕복달리기와 상대악력이 빠져 있었다.

- 10m 왕복달리기: ±8%p
- 상대악력: ±7%p

수정 후 실제 API에서 HOME 10m 결과가 `상위 0~9%`, 상대악력이 `상위 48~62%`로 나오는 것을 확인했다. CENTER 결과는 기존처럼 하나의 백분위 값으로 유지됐다.

당시 최종 확인 결과는 프론트 계약 38/38, 백엔드 인증·기록·대화 계약 36/36이었다. 이 숫자는 프로젝트 테스트 결과이며 테스트 파일 전체를 내가 단독으로 작성했다는 뜻은 아니다. 내가 맡은 부분은 발견된 불일치를 수정하고 실제 서버를 다시 실행해 응답까지 확인한 것이다.

## 5주차 — 9월 24일~9월 30일

### 현재 체력보다 한 단계 높은 운동 추천

결과 화면의 운동 영상이 단순히 같은 체력요인의 영상을 보여주는 데서 끝나지 않도록 추천 기준을 수정했다.

각 측정항목의 백분위를 영상 API로 보내고, 현재 수준보다 한 단계 높은 운동 주차를 선택하도록 했다. `나의 운동 추천` 버튼은 사용자가 측정한 항목 가운데 가장 부족한 항목을 기준으로 준비운동, 본운동, 마무리운동을 고르게 했다.

이때 화면의 `상위 %`를 해석하는 방향 때문에 한 번 더 확인이 필요했다. 현재 화면에서는 숫자가 클수록 수행이 낮은 경우가 있어서 일반적인 점수처럼 계산하면 추천 단계가 반대로 나온다. 악력 값을 바꿔 호출해 보면서 상위 95%, 55%, 20%에서 각각 다른 주차 운동이 선택되는지 확인했다.

### 26분 영상과 1분 영상 중 어느 것이 맞는지 확인

이전 버전에서는 준비운동, 본운동, 마무리운동에 26분 정도 되는 영상이 각각 표시됐다. 수정 뒤에는 1분 안팎의 짧은 영상이 나와서 어느 쪽이 맞는지 다시 원본을 확인했다.

성인 1주차 데이터는 186행이었지만 고유 영상 URL은 하나뿐이었다. 준비·본·마무리 운동 행이 모두 같은 1,586초짜리 전체 프로그램을 가리키고 있었다. 이전 화면은 서로 다른 세 영상을 보여준 것이 아니라 같은 26분 26초 영상을 세 번 반복해서 보여준 셈이었다.

짧은 영상은 특정 동작을 설명하는 국민체력100 운동처방가이드였다. 그래서 측정항목 옆 버튼과 개인 추천에는 짧은 동작 설명 영상을 사용하는 쪽이 맞다고 판단했다. 다만 영상 길이는 실제 운동 수행시간이 아니므로, 권장 횟수와 세트는 이후 화면에서 별도로 보여줄 필요가 있다. 26분 전체 프로그램도 없애기보다는 별도 버튼으로 한 번만 제공하는 편이 낫다고 정리했다.

### 실행 파일로 처음부터 다시 확인

코드를 수정한 상태에서 서버가 떠 있다는 것만 확인하지 않고 실제 배포 패키지의 CMD 파일로 완전히 종료하고 다시 실행했다.

- `STOP_AI_FITNESS.cmd` 실행
- 웹 서버와 Qwen3 포트가 모두 닫혔는지 확인
- `START_AI_FITNESS.cmd` 실행
- Python 환경과 필수 파일 검사
- Qwen3, Chroma, 웹 서버가 새 프로세스로 시작되는지 확인
- UI HTTP 200과 최신 패치 버전 확인
- 실제 브라우저에서 로그인부터 측정, 결과, 운동 추천까지 확인

다른 PC에서도 실행할 수 있도록 모델, Chroma 인덱스, 사용자 DB처럼 용량이 크거나 공개하면 안 되는 파일은 저장소에서 제외했다. GitHub에는 코드, 테스트, 실행 스크립트, 소형 규준 DB와 문서만 남겼다.

## 작업하면서 가장 오래 걸렸던 부분

### 연령대 문제는 점수 조정으로 해결되지 않았다

처음에는 어르신 영상에 점수를 더 주면 될 것이라 생각했지만 성인 영상이 계속 섞였다. 검색 결과를 점수로만 조정하지 않고 연령대를 먼저 필터링해야 문제가 끝났다.

### 화면이 열린다고 정상 동작하는 것은 아니었다

HTTP 200만 보면 대부분 정상처럼 보였다. 실제로는 다른 사용자 기록이 섞이거나, 만료 토큰이 계속 살아 있거나, HOME과 CENTER 결과가 같은 방식으로 표시되는 문제가 남아 있었다. 그래서 이후에는 API 응답, DB 상태, 브라우저 화면을 따로 확인했다.

### 원본 데이터의 한 행이 영상 한 개를 뜻하지 않았다

영상 데이터의 행 수만 보면 영상이 매우 많은 것처럼 보였지만 같은 파일 URL이 여러 운동 행에 반복되어 있었다. 26분 영상 문제는 행 수가 아니라 고유 URL을 확인하고 나서야 이해할 수 있었다.

## 최종 결과 중 내가 직접 확인한 범위

- Qwen3-4B 로컬 실행과 재시작
- Chroma RAG 문서 160,461건 로드
- 성별·연령대별 백분위 API
- HOME 구간과 CENTER 점 백분위
- 생애주기별 영상 필터
- 사용자별 측정 기록과 대화 분리
- 인증 세션 만료와 서버 대화 삭제
- 백분위에 따른 운동 추천 변화
- Windows CMD 종료·재실행
- 실제 브라우저의 로그인, 측정, 결과, 추천 흐름

프로젝트 전체 최종 결과는 공식 평가 145/145, RAG 검색 대상 80/80, R5 80/80, R8 65/65, R11 6/6, 단위·계약 테스트 54/54, 프론트 통합 계약 38/38, 백엔드 계약 36/36, 3인 블라인드 평가 12/12 다수결 PASS였다.

위 결과를 전부 내 개인 성과로 적지는 않았다. 공식 평가 세트와 블라인드 평가에는 다른 팀원의 작업도 포함되어 있다. 이 문서에는 그중 내가 직접 수정하거나 실행해서 확인한 백엔드 범위를 중심으로 기록했다.

## 아쉬웠던 점

- 1주차 작업은 대화 기록이 없어 코드 단위로 복원하지 못했다.
- 작업 중간에 실행 폴더가 여러 번 정리되어 공개 저장소와 실제 패키지 경로를 다시 맞추는 데 시간이 들었다.
- 운동 영상과 실제 권장 운동시간을 화면에서 완전히 분리하지 못했다.
- 자동 테스트만으로는 작은 화면의 스크롤 문제나 영상 데이터의 중복 의미를 찾기 어려웠다.
- 공개 저장소의 Git 기록만으로는 테스트 파일별 최초 작성자를 모두 구분하기 어렵다.
