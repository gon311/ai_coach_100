# 김민 백엔드 작업 기록

이 문서는 프로젝트가 끝난 뒤 기억에 의존해 작성한 회고가 아니다. 프로젝트 기간에 남긴 Codex의 AI 코칭 대화, 팀 노션의 주차 일정, 저장소 문서를 날짜순으로 다시 대조해 정리했다.

담당 범위는 백엔드 API, 사용자 기록 DB, 로컬 Qwen3·RAG 연결, 실행 패키지와 통합 검증이다. 화면을 고치는 과정에서도 API 계약이나 추천 로직을 함께 바꾼 경우가 있어 프론트 작업이 일부 등장하지만, 이 문서에서는 내가 확인하거나 수정한 백엔드 흐름을 중심으로 적었다.

## 기록을 정리한 기준

- 프로젝트 일정: 2026년 8월 26일 ~ 9월 30일, 5주
- 주차 구분: 팀 노션의 주차 일정 사용
- 직접 근거: Codex 대화에서 요청한 내용, 수정 파일, 실행 결과
- 보조 근거: `docs/planning`, 백엔드 테스트, 최종 실행 패키지
- 작성자를 확인할 수 없는 팀 산출물은 내 단독 성과로 적지 않음
- 자동 평가 결과는 개인 작성 범위와 프로젝트 전체 결과를 구분함

## 1주차 — 백엔드 구현 전 기준 정리

### 당시 상황

기획 단계에서는 공공데이터 한 종류로 또래 비교와 운동 추천을 모두 처리할 수 있을 것으로 봤다. 실제 데이터를 확인하면서 측정 데이터, 추천 데이터, 영상 데이터의 역할이 서로 다르다는 점이 드러났다. 백엔드는 이 데이터를 한 테이블처럼 다루기보다 용도별로 분리해 연결해야 했다.

### 내가 맡은 흐름

- 팀에서 정리한 측정 데이터 정규화 기준을 전달받아 백엔드 DB 구조와 연결할 항목을 확인했다.
- HOME과 CENTER 기록을 별도 테이블로 나누는 대신 `source` 값으로 구분하는 방향을 확인했다.
- 홈 측정값도 센터 규준 분포를 기준으로 계산하되, 화면에는 단일 점수가 아니라 오차를 반영한 구간으로 보여주는 계약을 검토했다.
- 절대악력(kg)과 상대악력(%)은 같은 값이 아니므로 별도 측정 행으로 저장해야 한다는 기준을 반영 대상으로 잡았다.
- 사용자 DB, 원본 공공데이터, 모델, 벡터 인덱스처럼 공개 저장소에 올리면 안 되는 파일을 구분하기 시작했다.

### 남아 있는 근거와 한계

Codex의 AI 코칭 대화 기록은 9월 7일부터 남아 있다. 따라서 1주차는 팀 문서에 기록된 백엔드 전달 내용까지만 확인되며, 이 시기의 세부 코드 작성량을 내 개인 성과로 단정하지 않았다.

## 2주차 — 로컬 AI와 서비스 백엔드 연결

### 9월 7일: 모델 실행 환경부터 분리

처음에는 E 드라이브의 Qwen UI가 어떤 모델과 연결되어 있는지부터 다시 확인했다. 27B 모델과 프로젝트에서 사용할 Qwen3-4B를 같은 포트에서 바꿔 쓰면 실행 상태를 확인하기 어려웠기 때문에 별도 실행 환경으로 분리했다.

- Qwen3.8 27B UI를 포트 `8088`에서 실행하도록 정리
- 프로젝트용 Qwen3-4B UI를 포트 `8089`로 분리
- Qwen3-4B는 `context_length=32768`, `max_new_tokens=8192`로 설정
- 시작·종료 PowerShell 스크립트를 각각 작성하고 종료 후 재시작까지 확인
- 짧은 응답이 내부 추론에 소모되지 않도록 `enable_thinking: false` 설정 확인

이 작업은 모델 자체를 개발한 것이 아니라, 이후 체력 코칭 서비스가 어느 모델을 호출하는지 재현할 수 있게 만든 실행 환경 정리였다.

### 프론트와 실제 백엔드 통합

`frontend1`의 화면은 있었지만 일부 기능이 MOCK 상태였다. 이를 실제 AI Fitness 백엔드와 연결하고, 한 번에 실행할 수 있는 진입점을 만들었다.

- 통합 서비스 주소를 `http://127.0.0.1:8501`로 구성
- 프론트 화면에서 실제 `/api/coach`, `/api/chat` 호출로 연결
- Qwen3-4B와 Chroma RAG 인덱스 연결 상태 확인
- RAG 문서 160,461건 로드 여부 확인
- 통합 시작·종료 스크립트 작성
- `/api/health`, 페이지 HTTP 200, 한국어 모델 응답을 각각 확인

### 백분위 API와 공식 영상 연결

측정값을 단순 점수로 보여주는 대신 성별과 5세 연령대가 같은 원본 기록의 분포와 비교하도록 백분위 흐름을 연결했다.

- 측정 코드와 백엔드 코드 매핑 확인
  - `FLEX_SIT_REACH`
  - `MUSC_END_SITUP`
  - `CARDIO_2MINSTEP`
  - `POWER_LONGJUMP`
  - `LOWER_CHAIRSTAND`
  - 상대악력
- 원본 55개 CSV, 1,433,939행을 집계해 비교 규준 생성
- 상대악력 필드와 절대악력 필드를 원본 정의서에서 다시 확인
- 사용자 악력 입력을 `악력÷체중×100`으로 환산해 상대악력 백분위와 연결
- 공식 국민체력100 영상 메타데이터를 조회하는 API 연결
- 운동 항목별 공식 영상 TOP 3 응답 확인

연령대마다 공식 측정 종목이 다르기 때문에 모든 축에 평균을 억지로 채우지 않았다. 성인은 유연성·근지구력·순발력, 어르신은 유연성·심폐지구력·하지근기능을 기본으로 하고, 악력은 장비가 있는 경우 선택하도록 했다. 동일 연령대 규준이 없는 항목은 다른 연령 평균으로 대체하지 않았다.

### 코칭 하네스 연결

- 결과 화면에서 선택한 취약 항목을 코칭 문맥으로 전달
- `/api/chat` → `qwen3_grounded_harness.py` → Qwen3-4B 호출 흐름 연결
- 운동 추천 응답, 후속 질문 문맥, 실제 모델 응답까지 순서대로 확인

관련 경로:

- `apps/api/src/fitness_web_server.py`
- `apps/api/src/fitness_mvp.py`
- `apps/api/src/qwen3_grounded_harness.py`
- `apps/api/src/center_percentile.py`
- `apps/api/scripts/`

## 3주차 — 사용자 기록과 생애주기 계약 정리

### 먼저 재현한 문제

72세 여성 테스트 계정에서 추천 영상을 조회했을 때 준비운동은 성인 영상, 본운동과 마무리운동은 어르신 영상이 나왔다. 어르신 영상 데이터가 없어서 생긴 문제가 아니었다. 후보 영상 점수에 연령대가 가산점으로만 들어가 있어, 검색어가 더 많이 겹친 성인 영상이 선택된 것이 원인이었다.

### 생애주기 영상 혼합 방지

- 프론트 요청에서 `age`와 `life_stage`를 함께 전달하도록 계약 정리
- 백엔드에서 나이로 계산한 생애주기와 전달받은 값이 일치하는지 검증
- 영상 후보를 점수만으로 고르지 않고 현재 생애주기·공통 영상으로 먼저 필터링
- `TEEN`, `ADULT`, `SENIOR`별 측정·영상 흐름 대조
- 성인 준비운동이 어르신 추천에 섞이는 재현 요청을 회귀 테스트로 사용

처음 수정 시도는 작업 세션의 보안 체크포인트 오류로 파일 반영이 막혔다. 새 작업에서 같은 문제를 다시 재현한 뒤 패치와 검증을 이어 갔다. 이 과정은 실패한 시도까지 기록에 남겨 두었다.

### 사용자 기록과 대화 분리

로그인만 된다고 사용자 분리가 끝나는 것은 아니었다. 다른 프로필로 바뀌었을 때 이전 측정 기록이나 대화가 섞이지 않는지 별도로 확인했다.

- 사용자별 측정 세션 조회
- 기록 소유자와 인증 사용자 일치 여부 확인
- 프로필 변경 시 기존 코칭 대화가 새 사용자 문맥에 들어가지 않도록 분리
- 비회원 세션 초기화와 로그인 사용자 기록 지속성 확인
- 이전 기록 비교 시 현재보다 미래 시점의 기록이 선택되지 않도록 조회 기준 점검

### HOME과 CENTER 결과 계약

- HOME은 자가측정 오차를 반영한 백분위 구간으로 반환
- CENTER는 측정 장비 결과이므로 점 백분위 유지
- 상대악력과 절대악력을 연령 기준에 맞게 구분
- 프론트에 표시되는 체력요인 명칭과 백엔드의 공식 요인 명칭 대조
- 상세 API 오류가 단순한 `api-unavailable`로 사라지지 않도록 오류 전달 경로 점검

관련 테스트:

- `apps/api/tests/test_age_bmi_recommendations.py`
- `apps/api/tests/test_fitness_web_server.py`
- 실행 패키지에 포함된 생애주기·기록·개인정보 계약 테스트

## 4주차 — 인증과 API의 남은 허점 보강

기능이 정상 동작해도 요청이 무한 대기하거나 오래된 토큰이 계속 유효하면 실제 배포에서는 문제가 된다. 이 주에는 앞선 통합 작업에서 남은 계약 차이를 줄이는 데 집중했다.

### 인증 요청 timeout

- 로그인, 회원가입, 프로필, 기록, 로그아웃 요청에 기본 30초 timeout 적용
- `AbortController`로 fetch 자체뿐 아니라 응답 JSON을 읽는 단계까지 취소 처리
- 서버가 응답하지 않을 때 화면이 계속 대기 상태에 남지 않도록 정리

### 인증 세션 만료

- 인증 세션 기본 TTL을 24시간으로 설정
- `AI_FITNESS_AUTH_TTL_HOURS` 환경변수로 운영 환경에서 조정 가능하도록 구성
- 만료됐거나 생성시각이 잘못된 토큰은 401 반환
- 만료 토큰과 연결된 서버 측 대화 기록도 함께 삭제
- 임시 만료 토큰을 넣어 API 호출 후 세션이 실제로 제거되는지 확인

### 백분위 구간 계약 보정

프론트 레이더 설정과 백엔드 HOME 구간 폭이 다른 항목을 찾아 맞췄다.

- 10m 왕복달리기: ±8%p
- 상대악력: ±7%p
- 기존 유연성·근지구력·심폐·순발력·하지근기능 설정과 함께 총 8종목 대조
- CENTER 응답은 구간으로 바꾸지 않고 점값을 유지

### 확인한 결과

- 프론트 통합 계약 38/38
- 백엔드 인증·기록·대화 계약 36/36
- 실제 HOME 10m 결과 `상위 0~9%`
- 실제 HOME 상대악력 결과 `상위 48~62%`
- CENTER 점 백분위 유지
- 만료 임시 토큰 401 및 잔여 세션 0건

위 수치는 프로젝트의 검증 결과다. 테스트 파일 전체를 내가 단독 작성했다는 뜻으로 사용하지 않는다. 내가 한 일은 남은 불일치를 재현하고, 관련 백엔드·프론트 계약을 수정한 뒤 실제 서버에서 다시 확인한 것이다.

## 5주차 — 추천 로직 마무리와 실행 패키지 검증

### 백분위 기반 다음 단계 운동 추천

결과 화면의 운동 영상은 단순히 같은 체력요인의 영상을 보여주는 데서 끝나지 않도록 수정했다.

- 각 측정항목의 백분위를 영상 추천 API에 전달
- 현재 수준보다 한 단계 높은 본운동을 선택하도록 주차 규칙 적용
- `나의 운동 추천`은 측정한 항목 중 수행 백분위가 가장 낮은 항목을 기준으로 선택
- 준비운동·본운동·마무리운동이 모두 반환되는지 확인
- 악력 예시에서 백분위별로 2·3·4주차 운동이 달라지는 것을 API로 검증

이때 화면의 `상위 %`는 숫자가 클수록 좋은 점수가 아니었다. 예를 들어 `상위 95%`는 분포상 낮은 수행을 뜻하는 현재 표기 규칙이어서, 추천 단계 계산에서 방향을 반대로 해석하지 않도록 수정했다.

### 26분 영상과 1분 영상의 의미 구분

이전 버전에서는 준비·본·마무리에 약 26분 영상이 각각 나왔다. 원본을 확인해 보니 서로 다른 세 영상이 아니라 동일한 전체 프로그램 파일 하나가 여러 운동 행에 반복 연결된 것이었다.

- 성인 1주차 186행이 고유 영상 파일 1개를 가리키는지 확인
- 전체 프로그램 길이 1,586초(26분 26초) 확인
- 짧은 영상은 특정 동작을 설명하는 `운동처방가이드`임을 확인

## 백엔드에서 해결한 문제를 다시 정리하면

### 1. 데이터가 있다고 바로 추천에 쓸 수 있는 것은 아니었다

측정 결과, 백분위 규준, 추천 규칙, 영상 메타데이터는 각각 역할이 달랐다. 측정 데이터로 사용자 위치를 계산하고, 추천 규칙으로 다음 운동을 고른 뒤, 영상 데이터에서 공식 출처를 연결하는 순서로 나눴다.

### 2. 점수 가산만으로는 생애주기 혼합을 막지 못했다

어르신 영상에 높은 점수를 주는 방식으로는 검색어가 많이 겹친 성인 영상을 완전히 막을 수 없었다. 그래서 `age`와 `life_stage`를 검증하고, 대상 연령을 필수 필터로 바꿨다.

### 3. 화면이 열리는 것과 서비스가 맞게 동작하는 것은 달랐다

HTTP 200만 확인하지 않고 실제 API 값, 브라우저 표시, 사용자 전환, 만료 토큰, 서버 재시작 뒤의 상태를 따로 확인했다. 이 과정에서 HOME 구간 폭, CENTER 점값, 인증 만료와 대화 삭제처럼 화면만 봐서는 찾기 어려운 문제를 수정했다.

### 4. 영상 길이와 운동 시간은 같은 값이 아니었다

1분짜리 동작 설명 영상은 1분만 운동하라는 의미가 아니었다. 반대로 26분짜리 프로그램 파일을 준비·본·마무리에 세 번 보여주는 것도 잘못된 표현이었다. 원본 데이터의 행과 고유 URL을 대조해 두 영상의 용도를 분리했다.

## 아쉬웠던 점

- 1주차 작업은 Codex 대화가 남아 있지 않아 개인 단위의 세부 구현을 복원하지 못했다.
- 여러 번 수정한 실행 폴더와 공개 저장소의 경로가 달라, 마지막에 파일을 다시 대조하는 시간이 많이 들었다.
- 영상 메타데이터에 전체 프로그램과 동작 가이드가 함께 있어 UI에서 용도를 더 명확히 나눌 필요가 있다.
- 자동 테스트는 계약 위반을 잘 잡았지만, 작은 화면 스크롤이나 실제 영상 의미는 브라우저와 원본 데이터를 직접 봐야 발견할 수 있었다.
- 현재 공개 저장소만으로는 각 테스트 파일의 최초 작성자를 모두 구분할 수 없다. 그래서 확인할 수 있는 수정·검증 범위만 개인 기여로 적었다.
