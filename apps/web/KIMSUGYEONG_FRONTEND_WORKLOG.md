# 프론트엔드 작업 기록 — 김수경

프로젝트에서 맡았던 프론트엔드·UX 작업을 주차별로 정리했다. 회의록, 화면 설계 문서, 프론트엔드 결정 로그와 검증 기록을 바탕으로 작성했다.

내가 주로 맡은 부분은 사용자가 기본정보를 입력하고, 안전문진과 체력측정을 거쳐 결과·운동 추천·AI 코치를 이용하는 화면이다. 초기 Mock 화면을 만든 뒤 웹 디자인을 다시 다듬었고, 색상·글자·카드·버튼과 랜딩·챗봇 이미지가 하나의 서비스처럼 보이도록 맞췄다. 프로젝트 후반에는 화면과 백엔드의 측정·인증·채팅 계약이 맞는지 백엔드 담당자와 함께 확인했다.

- 기간: 2026년 8월 26일~9월 30일 (약 5주). 주차 구분은 팀원 작업 기록과 같다.
- 기술: Vue 3(CDN), JavaScript, HTML, CSS, Figma
- 구현 단계 P0~P4는 주차가 아니라 작업 단계이며, 여러 단계가 같은 주에 진행됐다.
- 통합 패키지의 인증·프로필 작업은 백엔드 담당자와의 공동 작업이다. 공개 저장소에 없는 자료는 ‘로컬 보관’으로 표시했다.

## 1주차 — 8월 26일~9월 2일

### 프론트엔드 개발 순서와 협업 기준 정리

AI 체력코치 MVP에 필요한 화면과 개발 순서를 정리했다. 백엔드와 데이터 전처리가 끝나기 전에도 화면 작업을 진행할 수 있도록 Mock 데이터로 먼저 만들고, 이후 실제 API에 연결하는 방향을 잡았다.

`AI 체력코치 MVP Frontend 개발 작업 순서` 문서에는 화면 이동부터 인증, 측정, 리포트, 운동 추천, 영상과 AI 코치까지 24단계의 작업 순서를 정리했다. 로딩·오류·재시도, 측정 이력과 통합 테스트도 개발 항목에 포함했다.

역할은 프론트가 사용자 입력과 결과 표현을, 백엔드가 체력 분석·운동처방 계산·DB 저장·RAG·LLM 처리를 맡도록 나눴다. 협업에서는 DB 내부 구조보다 API의 요청·응답·오류 형식을 먼저 맞추는 것이 중요하다고 정리했다. 문서에 적은 React·TypeScript 기반 구성은 당시 제안안이었고, 실제 구현은 팀 상황에 맞춰 Vue 3로 진행했다.

### 모바일형 Mock 프로토타입 제작

8월 31일 초기 화면 제작을 시작해 9월 4일 완료했다. 짙은 녹색 헤더와 주황색 버튼, 카드형 입력·결과 영역으로 모바일 앱처럼 읽히도록 구성했다.

- 랜딩: 서비스 소개와 체력 측정 시작
- 로그인: 아이디·비밀번호 입력 (Mock)
- 기본정보: 성별, 나이, 키, 체중
- 측정 경로: CENTER 결과 입력과 HOME 자가측정 선택
- PAR-Q: 7개 사전 안전문진
- 홈 측정 가이드: 교차윗몸일으키기, 앉아윗몸앞으로굽히기, 제자리멀리뛰기와 선택 악력
- 측정 입력·결과 확인: 종목별 입력란과 단위 표시
- 리포트: 측정 원값, 또래 비교(Mock), 강점·약점과 미측정 항목 안내
- 운동 추천·운동 영상: 기본·보완 운동 카드와 국민체력100 영상 목록

Mock 단계임을 화면에 분명히 표시했다. 로그인에는 `Mock으로 로그인`, 리포트에는 Mock 데이터 기준, 운동 추천과 영상에는 실제 콘텐츠 연결 전이라는 안내를 두었다. 초기 계획의 종합점수·등급·오각형 그래프는 이후 팀 협의를 거쳐 백분위 중심 표시로 바뀌었다.

관련 자료: `docs/planning/meeting-01/weekly_action_plan.md`, 개발 작업 순서 문서와 1주차 화면 모음(로컬 보관)

## 2주차 — 9월 3일~9월 9일

### 프로토타입에서 서비스 디자인으로

9월 4일 Mock 화면을 완성한 뒤, 기능 배치를 넘어 실제 서비스로 쓸 수 있는 디자인을 다듬었다. 9월 7~8일에는 성인·시니어 측정 영상 연결과 재생 오류를 보완하고, 누락된 측정항목을 복원했다.

9월 8일에는 녹색·주황색 화면을 흰색·파란색 중심 디자인으로 바꿨다. Figma에서 모바일 온보딩 5개 화면을 구성하고 SVG·PNG 산출물을 만든 뒤 전체 웹뷰에 적용했다. 제목·설명·입력값·버튼의 시각적 우선순위를 정리하고, 카드 여백과 테두리, 버튼 크기와 강조색을 통일했다. 측정값과 또래 평균은 색으로 구분하고, 미측정·비교 준비 중·오류 상태에는 설명을 함께 표시했다.

### 레이더 차트가 점수처럼 보이지 않게

종목마다 단위와 범위가 달라 측정 원값을 그대로 차트에 넣을 수 없었다. 반대로 화면 표시용으로 변환한 값을 체력점수라고 부르면 사용자가 결과를 오해할 수 있었다. 그래서 레이더 차트의 위치값과 백엔드가 계산하는 백분위를 분리했다.

- 레이더 차트는 측정 원값을 종목별 표시 범위 안에서 시각화하고, 축에 실제 값과 단위를 표시
- 또래 평균과 백분위는 백엔드가 제공할 때만 표시
- 미측정 항목은 `null`로 두고 0점으로 바꾸지 않음
- 일부 항목만 측정했으면 측정된 점과 인접 선분만 표시
- 공식 인증등급이나 프론트에서 만든 종합점수는 표시하지 않음

9월 9일 회의에서 악력·심폐지구력을 측정하지 못한 경우를 논의했고, 모든 축을 채운 도형 대신 실제로 측정한 항목만 보여주는 방향으로 정했다.

### 모바일 측정 흐름 정리

기본정보 → 안전문진 → HOME/CENTER 선택 → 측정 → 결과로 이어지는 흐름을 정리했다.

- 성인·시니어 HOME 측정항목과 CENTER 입력 구분
- 유연성 음수 입력 허용 등 종목별 입력 검증
- 만 19세 미만의 미확정 측정 경로 차단
- PAR-Q 결과에 따른 홈 측정 제한과 센터 안내
- 측정 가이드와 운동 영상의 화면 내 재생

9월 9일 P1 검증에서 모바일 흐름, 부분 레이더, 미측정 표시와 영상 오류 안내를 확인했다.

## 3주차 — 9월 10일~9월 16일

### 고정 폭 화면을 반응형 웹으로 전환

초기 화면은 모바일 앱처럼 고정 폭이라, 넓은 화면에서도 작은 크기로 남는 문제가 있었다. 9월 9일 회의에서 정한 반응형 방향에 맞춰 9월 11일 전환을 마쳤다.

- 모바일은 전체 화면, 태블릿은 여백 있는 화면, 데스크톱은 본문 폭을 읽기 좋게 제한
- 넓은 화면에서 HOME/CENTER 선택과 입력 카드를 다열 배치
- 데스크톱 리포트에서 레이더 차트와 상세 측정값을 나란히 배치
- 상단 바, 하단 버튼, 모달 동작과 영상 16:9 비율 정리

화면 폭 320~1920px에서 배치를 확인하고, 키보드 포커스·모달 닫기·포커스 복귀를 점검했다. 실제 iOS·Android 기기 검증은 남은 과제로 기록했다.

화면마다 먼저 읽어야 할 내용과 눌러야 할 버튼도 다시 정리했다. 리포트는 나의 측정값, 또래 비교, 미측정 항목, 추천 행동을 구분해 그래프만 보고 끝나지 않도록 했다.

### 화면 코드와 API 접근 코드 분리

화면이 커지면서 설정값, 계산 함수, API 요청이 한 파일에 섞였다. 9월 9~11일 기존 동작을 유지하면서 JavaScript를 역할별로 나눴다.

- `config`: 측정항목, 레이더, 영상 설정
- `data`: Mock 운동 추천 데이터
- `utils`: 측정값 변환, 레이더·영상 보조 함수
- `services`: 백분위, 리포트, 영상 API 요청
- `app.js`: 화면 상태, 이동, 사용자 이벤트

## 4주차 — 9월 17일~9월 23일

> 이 주의 연동 작업은 통합 패키지(로컬 최종본) 기준이다. 공개 저장소의 `apps/web`에는 아직 반영되지 않았으며, 최종본 동기화 후 이 안내를 삭제할 예정이다.

### 최종 프론트와 실제 API 계약 맞추기

9월 17일 화면의 측정 코드와 실제 API 요청·응답을 대조하고, 게스트와 로그인 사용자 흐름을 나눴다. 화면의 입력 조건·표시 방식·상태 전환은 내가, 서버의 계산·인증·DB 처리는 백엔드 담당자가 맡고, 둘을 맞추는 과정은 함께 진행했다.

- 측정·요약·채팅 요청을 공통 서비스에서 처리
- 게스트 채팅에는 현재 측정 정보와 대화 ID, 로그인 채팅에는 Bearer 토큰과 대화 ID 전달
- 새 게스트로 시작하면 이전 입력값·측정 결과·대화 초기화
- 늦게 도착한 이전 요청이 새 화면을 덮어쓰지 않도록 처리
- API 실패·응답 누락·로딩 상태를 화면에서 구분

### HOME 구간과 CENTER 점 백분위 구분

자가측정과 센터 측정 결과가 같은 방식으로 보이지 않도록, HOME은 팀이 정한 표시 폭을 쓰는 구간으로, CENTER는 점 백분위로 표시했다. 9월 17일에는 빠져 있던 10m 왕복달리기 ±8%p, 상대악력 ±7%p 표시 폭을 추가했다. 구간은 0~100으로 제한하되 원본 측정값과 백엔드 백분위는 바꾸지 않았다. 이 폭은 화면 표시 정책이며 통계적 신뢰구간이 아니다.

### 실패와 재시도 흐름 보완

- 안전 안내에서 CENTER로 이동할 때 올바른 입력 경로 사용
- 입력란 label·ID 연결, 악력 선택 버튼의 키보드 접근성 개선
- 채팅 실패 후 같은 대화에서 재시도, 중복 요청 방지
- 측정·채팅·요약·영상·인증 요청의 시간 제한과 취소 처리

### 인증·프로필 저장 공동 확인

이름을 필수로 받는 기존 백엔드 계약과 최소 정보만 받는 프론트 정책이 충돌했다. 문제를 기록해 백엔드 담당자와 계약을 맞췄고, 통합 패키지에서 최소 정보 회원가입, 로그인, 프로필 수정, 새로고침·재로그인 후 값 복원을 확인했다. 인증 API와 DB 구현은 백엔드 담당자의 작업이며, 나는 화면 요구사항과 연동 확인을 맡았다.

검증 결과는 프론트 계약 38/38, Mock 브라우저 24/24다. 시점과 범위가 다른 결과라 합산하지 않았고, Mock 브라우저 통과를 실제 서버 연동 성공으로 대신하지 않았다.

### 이미지 표시 완성도 점검

통합 화면에서 메인 이미지가 다른 요소에 눌려 작아지지 않도록 축소를 막고, 화면 폭에 맞춰 16:9 비율을 유지하게 했다. 9월 17일 확인 환경에서 메인 이미지가 472 × 265.5px로 잘림 없이 표시됐다. CSS와 스크립트에 버전값을 붙여 이전 캐시 때문에 수정 전 화면이 남지 않게 했다.

## 해결한 주요 문제

**디자인은 화면 전체의 일관성 문제였다.** 개별 카드나 이미지가 보기 좋아도 제목·버튼·여백이 화면마다 다르면 하나의 서비스로 느껴지지 않았다. 공통 색상과 표현을 맞추고, 이미지 크기와 비율은 실제 브라우저 배치에서 다시 확인했다.

**보기 좋은 도형과 정확한 의미는 달랐다.** 미측정 항목을 0으로 채우면 도형은 쉽게 그려지지만 사용자는 낮은 체력으로 오해한다. 측정한 항목만 그리고 원값과 백분위를 나눠 설명했다.

**화면이 있다고 기능이 완료된 것은 아니었다.** 로그인 화면이 있어도 인증 API와 필수 입력값이 맞지 않으면 쓸 수 없었다. 계약이 없는 단계는 차단 상태로 두고, 계약을 맞춘 뒤 저장·복원 흐름을 확인했다.

**정상 응답만큼 상태 전환과 실패가 중요했다.** 새 게스트로 시작했는데 이전 입력이 남거나 늦은 응답이 새 결과를 덮어쓰면 화면은 열려 있어도 잘못된 상태다. 초기화, 요청 취소, 실패 안내와 재시도를 사용자 흐름의 일부로 다뤘다.

## 내 역할과 협업 범위

- 주 담당: 웹 디자인, 프론트엔드 화면, 반응형 UX, 측정·리포트·추천·AI 코치 UI
- 시각 요소: 색상·타이포그래피·카드·버튼 일관성, 랜딩·챗봇 이미지 배치와 표시 점검
- 화면 정책 반영: 미측정 처리, 원값과 백분위 분리, HOME/CENTER 표시 구분
- 협업: 백엔드 API 계약, 최소 정보 인증·프로필, 채팅 문맥과 실제 연동 확인
- 다른 팀원 담당: 원본 데이터 EDA·규준 산출, RAG/LLM 구축, DB·인증 서버 구현, 클라우드 운영과 공식 평가 실행

## 배운 점과 아쉬운 점

**처음 배우는 프론트엔드를 실제 프로젝트에 적용했다.** 화면 구조, 스타일, 상태 관리, API 연결, 반응형 디자인을 이번에 처음 접하고 필요한 개념을 찾아가며 적용했다. 시행착오가 많았고 원하는 디자인을 더 능숙하게 구현하지 못한 점은 아쉽다. 대신 프론트엔드가 화면뿐 아니라 데이터와 사용자 흐름을 함께 다루는 일이라는 것을 배웠다.

**변경은 기존 기능 확인과 함께 가야 했다.** 피드백을 반영하며 측정항목과 결과 표시 방식이 바뀔 때마다 프론트와 백엔드의 측정 코드·입력 조건·응답 형식을 다시 맞춰야 했다. 다음 프로젝트에서는 화면 흐름과 API 계약을 초기에 정리하고, 변경 사항을 공유하며 핵심 기능을 비교·확인하는 습관을 갖추고 싶다.

**완성도는 실제 환경에서 확인해야 했다.** 이미지 파일을 프로젝트 폴더에 넣어 전달했지만 다른 실행 환경에서는 표시되지 않아 파일명과 서버 경로를 다시 확인한 적이 있다. 앞으로는 작업본과 배포본을 명확히 관리하고, 여러 화면 크기와 실제 실행 환경에서 표시 상태까지 확인하려 한다.
