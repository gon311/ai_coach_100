# 프론트엔드 작업 기록 — 김수경

프로젝트에서 맡았던 프론트엔드와 UX 작업을 주차별로 정리했다. 회의록, 화면 설계 문서, 프론트엔드 결정 로그와 검증 기록을 함께 확인했다. 기록으로 확인되지 않는 세부 날짜와 개인별 작성 범위는 임의로 채우지 않았다.

내가 주로 맡은 부분은 사용자가 기본정보를 입력하고, 안전문진과 체력측정을 거쳐 결과·운동 추천·AI 코치를 이용하는 화면이었다. 초기 Mock 화면을 만든 뒤에는 웹 디자인을 다시 다듬고, 색상·글자·카드·버튼과 랜딩·챗봇 이미지가 하나의 서비스처럼 보이도록 신경 썼다. 프로젝트 후반에는 화면과 백엔드의 측정·인증·채팅 계약이 맞는지 백엔드 담당자와 함께 확인했다.

프로젝트 기간은 2026년 8월 26일부터 9월 30일까지 약 5주였다. 아래 주차는 팀원의 작업 기록과 같은 구간으로 나눴다. 구현 단계인 P0~P4는 주차를 뜻하지 않으며, 여러 단계가 같은 주에 진행됐다.

기록 기준: 초기 화면의 제작 완료일은 본인 확인에 따라 9월 4일로 기록했다. 4~5주차는 백엔드 담당자와 협업한 기간이며 일부 세부 기록이 남아 있지 않아, 확인 가능한 대화와 본인의 설명을 바탕으로 정리했다. 통합 패키지의 인증·프로필 수정은 공동 작업으로 구분했다.

자료 구분: 관련 문서의 경로는 공개 저장소 기준으로 적었다. 공개 저장소에 포함되지 않은 자료는 ‘로컬 보관’ 또는 ‘본인 제공’으로 표시했다. 작업 당시의 로컬 파일 경로는 현재 공개 저장소의 구조와 다를 수 있다.

## 1주차 — 8월 26일~9월 2일

### 프론트엔드 개발 순서와 협업 기준 정리

첫 주에는 AI 체력코치 MVP에서 어떤 화면이 필요하고 어떤 순서로 개발할지 정리했다. 백엔드와 데이터 전처리가 끝나기 전에도 화면 작업을 진행할 수 있도록 Mock 데이터로 먼저 만들고, 이후 실제 API에 연결하는 방향을 잡았다.

`AI 체력코치 MVP Frontend 개발 작업 순서` 문서에는 프로젝트 구조와 화면 이동부터 인증, 측정, 리포트, 운동 추천, 영상과 AI 코치까지 24단계의 작업 순서를 정리했다. 화면뿐 아니라 로딩·오류·재시도, 측정 이력과 삭제, 통합 테스트도 개발 항목에 포함했다.

프론트는 사용자 입력과 분석 결과의 화면 표현을 맡고, 체력 분석·운동처방 계산·DB 저장·RAG·LLM 처리는 백엔드가 맡도록 역할을 구분했다. 협업 시에는 DB 내부 구조보다 API의 요청·응답·오류 형식을 맞추는 것이 중요하다고 정리했다.

문서의 React·TypeScript·Vite, MSW, TanStack Query, Zustand와 JWT/HttpOnly Cookie는 당시 제안한 기술 구성과 인증 방향이다. 해당 도구를 모두 적용했거나 인증 기능을 첫 주에 완료했다는 의미는 아니다. 운동동기·IPAQ·노쇠 설문과 단계별 자동 저장도 개발 계획에 포함된 항목이며, 첨부 화면으로 구현 완료가 확인되는 범위와 구분했다.

### 모바일형 Mock 프로토타입 제작

8월 31일 대화에서 초기 프론트엔드 구현을 요청한 기록이 확인된다. 첫 주에 시작한 초기 화면 제작은 9월 4일에 완료했다. 작업 시작과 완료가 주차 경계에 걸쳐 있으므로, 아래에는 첫 주의 제작 내용을 정리하고 완료일은 2주차에도 명시했다.

계획과 함께 서비스의 핵심 흐름을 볼 수 있는 초기 화면을 제작했다. 짙은 녹색 헤더와 주황색 주요 버튼, 카드형 입력·결과 영역을 사용해 모바일 앱처럼 읽을 수 있도록 구성했다.

- 랜딩: 서비스 소개와 체력 측정 시작 버튼
- 로그인: 아이디·비밀번호 입력과 Mock 로그인 표시
- 기본정보: 성별, 나이, 키와 체중 입력
- 측정 경로: CENTER 측정 결과 입력과 HOME 자가측정 선택
- PAR-Q: 7개 사전 안전문진의 예·아니오 선택
- 홈 측정 가이드: 교차윗몸일으키기, 앉아윗몸앞으로굽히기, 제자리멀리뛰기 안내와 선택 악력
- 측정 입력: 종목별 입력란과 횟수·거리·악력 등의 단위 표시
- 결과 확인: 입력값을 다시 확인하고 리포트로 이동하는 화면
- 리포트: 측정 원값, Mock 또래 비교, 강점·약점과 미측정 항목 안내
- 운동 추천: 기본 운동과 약점 보완 운동 카드
- 운동 영상: 국민체력100 콘텐츠 목록과 영상 진입 UI

초기 리포트에는 측정값을 막대 형태로 보여주고, 측정하지 않은 근력·심폐지구력은 별도 안내 영역으로 구분했다. 결과에서 운동 추천과 체력인증센터 안내로 이어지는 화면도 구성했다.

### 실제 기능과 Mock 화면 구분

이 시기의 목적은 서비스 흐름과 화면 구성을 먼저 구체화하는 것이었다. 로그인에는 `Mock으로 로그인`, 리포트에는 Mock 데이터 기준, 운동 추천에는 실제 처방 콘텐츠 연결 전이라는 표시를 두었다. 영상 목록도 실제 영상 연결 전 단계임을 안내했다.

첫 주에는 개발 순서·협업 기준을 정리하고 초기 Mock 프로토타입 제작을 시작했다. 실제 회원가입·인증, 설문 자동 저장, 백분위 계산, RAG 기반 처방과 영상 재생까지 완료한 것으로 기록하지 않았다. 초기 계획에 포함된 종합점수·등급·오각형 그래프는 이후 협의를 거쳐 백분위 중심의 표시 정책으로 변경됐다.

## 2주차 — 9월 3일~9월 9일

9월 4일 초기 Mock 화면 제작을 완료한 뒤, 영상 가이드와 웹 디자인을 개선했다. 9월 7~8일에는 성인·시니어 측정 영상 연결과 재생 오류를 보완하고, 누락된 측정항목을 복원했다. 단일 HTML과 분리형 CSS·JavaScript·문서를 같은 버전으로 맞추는 작업도 진행했다.

### 초기 프로토타입에서 서비스 디자인으로 발전

첫 주에는 필요한 화면과 흐름을 빠르게 확인할 수 있는 Mock 프로토타입을 만들었다. 이후에는 기능을 배치하는 데서 한 걸음 더 나아가, 사용자가 실제로 이용할 웹 서비스의 디자인을 다듬었다.

9월 8일에는 초기의 녹색·주황색 화면에서 흰색·파란색을 중심으로 한 디자인으로 변경했다. Figma에서 모바일 온보딩 5개 화면을 구성하고 SVG·PNG 산출물을 만든 뒤 전체 웹뷰 디자인에 적용했다. 제목·설명·입력값·주요 버튼의 시각적 우선순위를 정리하고, 카드의 여백과 테두리, 버튼 크기와 강조색도 일관되게 맞췄다. 기본정보 입력과 측정 안내는 읽기 쉽게, 리포트는 결과를 먼저 파악하고 다음 행동으로 이어질 수 있도록 구성했다. 관련 변경은 `style.css`, `app.js`, `docs/index.html`에 반영했다.

특히 측정값과 또래 평균을 색상으로 구분하고, 미측정·비교 준비 중·오류 상태는 설명을 함께 표시했다. 보기 좋은 화면을 만드는 것과 사용자가 결과를 정확히 이해하도록 만드는 것을 함께 고려했다.

### 측정 결과의 의미를 화면에 맞추기

화면에서 가장 신경 쓴 부분은 레이더 차트가 실제 체력점수나 백분위처럼 보이지 않도록 하는 것이었다. 종목마다 단위와 범위가 달라 측정 원값을 그대로 차트에 넣을 수 없었다. 그렇다고 화면 표시용으로 변환한 값을 체력점수라고 부르면 사용자가 결과를 잘못 이해할 수 있었다.

그래서 레이더 차트의 위치값과 백엔드가 계산하는 백분위를 구분했다.

- 레이더 차트는 측정 원값을 종목별 표시 범위 안에서 시각화
- 축에 실제 측정값과 단위를 표시
- 또래 평균과 백분위는 백엔드에서 제공할 때만 표시
- 미측정 항목은 `null`로 유지하고 0점으로 바꾸지 않음
- 일부 항목만 측정했을 때는 측정된 점과 인접 선분만 표시
- 공식 인증등급이나 프론트에서 만든 종합점수는 표시하지 않음

9월 9일 회의에서도 악력과 심폐지구력을 측정하지 못한 경우의 표시 방식을 논의했다. 모든 축을 채운 도형을 만드는 것보다, 실제로 측정한 항목만 보여주는 방향으로 정리했다.

### 모바일 측정 흐름과 리포트 개선

기본정보, 안전문진, HOME/CENTER 선택, 측정과 결과 화면을 이어지는 흐름으로 정리했다. 성인과 만 65세 이상 사용자의 측정항목을 구분했고, 선택 악력과 미측정 상태도 따로 처리했다.

- 성인·시니어 HOME 측정항목과 CENTER 입력 구분
- 유연성의 음수 입력 허용 등 종목별 입력 검증
- 만 19세 미만의 미확정 측정 경로 차단
- PAR-Q 결과에 따른 홈 측정 제한과 센터 안내
- 측정 후 리포트로 바로 연결
- 측정 가이드와 운동 영상의 웹 화면 내 재생

## 3주차 — 9월 10일~9월 16일

### 화면별 디자인과 정보 배치 다듬기

디자인 변경은 색상 교체에서 끝내지 않았다. 랜딩, 기본정보, 측정 가이드, 리포트와 운동 추천 화면마다 사용자가 먼저 읽어야 할 내용과 눌러야 할 버튼을 정리했다. 선택 카드는 경로의 차이를 쉽게 비교하도록 하고, 측정 화면은 안내와 입력에 집중할 수 있도록 구성했다.

리포트에서는 나의 측정값, 또래 비교, 미측정 항목과 추천 행동을 구분했다. 레이더 차트와 범례, 상세 수치의 위치를 조정해 그래프만 보고 끝나는 것이 아니라 결과의 의미를 읽을 수 있도록 했다. 운동 추천은 순서와 구성을 파악하기 쉬운 카드로, AI 코치는 결과 화면에서 바로 열 수 있는 대화창으로 다듬었다.

작은 화면에서는 한 열로 자연스럽게 읽히고, 넓은 화면에서는 카드와 결과를 나란히 볼 수 있도록 배치를 조정했다. 같은 디자인을 화면 크기에 맞게 유지하는 과정도 프론트엔드 작업의 중요한 부분이었다.

### 고정 폭 화면을 반응형 웹으로 전환

초기 화면은 모바일 앱처럼 보이는 고정 폭 구조였다. 화면이 넓어져도 작은 화면 크기로 남는 문제가 있어, 9월 9일 회의에서 정한 반응형 웹 방향에 맞춰 수정했다. 9월 11일 대화에는 반응형 구현 완료와 데스크톱 전체 폭 보완 기록이 남아 있다. 주요 변경 파일은 `style.css`와 `app.js`의 화면 표시 클래스, P3 설계·검증 문서였다.

- 모바일은 전체 화면, 태블릿은 여백이 있는 화면 구성
- 데스크톱은 전체 화면을 활용하되 본문은 읽기 좋은 폭으로 제한
- 넓은 화면에서 HOME/CENTER 선택과 입력 카드의 다열 배치
- 데스크톱 리포트에서 레이더 차트와 상세 측정값의 나란한 배치
- 본문 스크롤, 상단 바, 하단 버튼과 모달의 동작 정리
- 영상의 16:9 비율과 좁은 화면의 가로 넘침 점검

브라우저에서 화면 폭을 320~1920px로 바꿔 모바일부터 데스크톱까지의 배치를 확인했다. 키보드 포커스, 모달 닫기와 포커스 복귀도 점검했다. 실제 iOS·Android 기기 검증은 별도 한계로 남겼다.

### 화면 코드와 API 접근 코드 분리

화면이 커지면서 설정값, 계산 보조 함수와 API 요청이 한 파일에 섞이는 문제를 정리했다. 9월 9일 작업을 시작해 9월 11일 완료한 기록이 확인된다. Vue와 기존 화면 구조를 유지하면서 JavaScript를 역할별로 분리했다.

- `config`: 측정항목, 레이더, 영상 설정
- `data`: Mock 운동 추천 데이터
- `utils`: 측정값 변환, 레이더와 영상 보조 함수
- `services`: 백분위, 리포트, 영상 API 요청
- `app.js`: 화면 상태, 이동과 사용자 이벤트

이 작업은 측정 정책을 새로 만드는 것이 아니라 기존 동작을 유지하면서 수정 위치를 분명하게 하는 데 목적이 있었다.

인증 API, DB 저장과 서버 재시작 검증은 백엔드 담당자의 작업에도 포함된다. 이 문서에서는 화면 요구사항과 연동 확인을 내 역할로 정리하며, 해당 변경 전체를 단독 구현 성과로 적지 않는다.

## 작업하면서 해결한 주요 문제

### 디자인은 화면 전체의 일관성을 맞추는 작업이었다

개별 카드나 이미지가 보기 좋아도 제목, 버튼과 여백이 화면마다 다르면 하나의 서비스처럼 느껴지기 어려웠다. 공통 색상과 표현을 맞추고, 이미지가 들어간 뒤에도 화면의 균형과 다음 행동이 유지되는지 확인했다. 특히 이미지 크기와 비율은 파일 자체보다 실제 브라우저 배치에서 다시 점검해야 했다.

### 레이더 차트의 보기 좋은 도형과 정확한 의미는 달랐다

미측정 항목을 0으로 채우면 도형은 쉽게 그릴 수 있지만 사용자는 낮은 체력으로 오해할 수 있었다. 실제 측정한 항목만 그리고, 원값과 백분위를 분리해 설명하는 방향으로 정리했다.

### 화면 구현과 실제 기능 완료를 구분해야 했다

로그인 화면이 있어도 인증 API와 필수 입력값이 맞지 않으면 실제 사용은 불가능했다. 계약이 없는 단계는 차단 상태로 기록하고, 계약을 맞춘 뒤 저장·복원 흐름을 확인했다.

### 정상 응답뿐 아니라 상태 전환과 실패도 중요했다

새 게스트로 시작했는데 이전 입력이 남거나 오래 걸린 응답이 새 결과를 덮어쓰면 화면은 열려 있어도 잘못된 상태였다. 초기화, 요청 취소, 실패 안내와 재시도를 사용자 흐름의 일부로 다뤘다.

- 협업: 백엔드 API 계약, 최소 정보 인증·프로필, 채팅 문맥과 실제 연동 확인
- 다른 팀원의 담당 영역: 원본 데이터 EDA·규준 산출, RAG/LLM 구축, DB·인증 서버 구현, 클라우드 운영과 공식 평가 실행

자동 테스트 결과는 해당 시점의 프로젝트 검증 기록이다. 테스트 전체와 백엔드 수정 전체를 내가 단독 작성했다는 뜻은 아니다. 파일별 개인 작성 범위가 확인되지 않는 부분은 협업 결과로 남겼다.

## 작업하면서 배운 점과 아쉬웠던 점

### 처음 배우는 프론트엔드를 실제 프로젝트에 적용했다

프론트엔드를 정식으로 배운 경험이 없어, 필요한 개념을 찾아보면서 프로젝트를 진행했다. 화면 구조와 스타일, 상태 관리, API 연결과 반응형 디자인 등을 이번 작업에서 처음 접하고 적용했다.

익숙하지 않아 시행착오와 반복 확인에 시간이 들었고, 원하는 디자인과 사용성을 더 능숙하게 구현하지 못한 점은 아쉬웠다. 다만 직접 적용하고 수정하면서 프론트엔드가 화면뿐 아니라 데이터와 사용자 흐름을 함께 다루는 작업임을 배웠다.

### 변경사항을 반영하면서 기존 기능도 함께 확인해야 했다

프로토타입을 함께 검토하고 피드백을 반영하면서 측정항목, 화면 구성과 결과 표시 방식을 구체화했다. 이 과정에서 프론트와 백엔드의 측정 코드·입력 조건·응답 형식을 다시 맞추고, 기존 기능이 유지되는지도 확인해야 했다.

변경의 영향을 미리 예상하고 관리하는 데 익숙하지 않아 반복 수정이 필요했다. 다음 프로젝트에서는 화면 흐름과 API 계약을 초기에 정리하고, 변경사항을 공유하며 핵심 기능을 비교·확인하는 습관을 갖추고 싶다.

### 이미지와 화면 완성도는 실제 환경에서 확인해야 했다

랜딩과 챗봇 이미지가 서비스 분위기에 어울리도록 신경 썼고, 크기·비율·잘림과 주변 요소의 균형을 조정했다. 이미지 파일을 프로젝트 폴더에 포함해 전달했지만, 다른 실행 환경에서는 표시되지 않아 파일명과 서버 경로를 확인한 경험도 있었다.

이 경험을 통해 디자인과 파일 전달만으로 작업이 끝나는 것은 아니라는 점을 배웠다. 앞으로는 작업본과 배포본을 명확히 관리하고, 다양한 화면 크기와 실제 실행 환경에서 표시 상태까지 확인해 완성도를 높이고 싶다.

## 프로젝트 종료 후 정리

10월 1~2일에는 공개 GitHub 저장소와 로컬 최종 프론트의 차이를 확인하고 누락 업데이트와 작업 기록을 정리했다. 이는 5주 프로젝트 기간의 구현과 구분하는 후속 작업이다. 프론트 동기화 준비본의 검증 결과를 9월 프로젝트 실적으로 소급하지 않았다.

## 관련 코드

- `apps/web/js/app.js`: 화면 상태, 이동, 측정·리포트·대화 흐름
- `apps/web/css/style.css`: 반응형 레이아웃과 접근성 표현
- `apps/web/js/config/`: 측정항목과 레이더·영상 설정
- `apps/web/js/utils/`: 측정·레이더·영상 보조 함수
- `apps/web/js/services/`: 백엔드 API 접근
- `docs/frontend/`: 설계 결정과 단계별 검증 기록

공개 저장소와 최종 로컬 파일은 같은 버전이 아닐 수 있다. 최종 프론트 기준 폴더는 로컬 `AI_fitness_frontend`이며, 공개 저장소에서의 대응 위치는 `apps/web`이다.
